## What the submitted plan gets right

- It identifies the active deploy-fitness mission's rejection of research tiers and Stage-2 automation, and places both behind explicit operator decisions.
- It adds the missing propagation prerequisite for canonical references, project-instantiated references, and runtime files.

## Initial findings, ordered by severity

### P0 — The plan drops the judgment-layer operating outcome and defers its canonical adoption unconditionally

**Factual finding.** The judgment plan defines the required sequence as `research → interpretation → Axcíon judgment → approved House View → publishing`, requires founder approval before serious content, and specifies expanded Unit Judgment Brief, insight extraction, insight ladder, evidence/context separation, independent QC, fail-closed re-entry, and downstream thesis control (`plans/canonical-research-workflow-judgment-and-insight-plan.md:8-23,83-223`). Its implementation sequence places a representative local trial first, but then explicitly continues through canonical foundation, producer/approval, orchestration, propagation/QC, deployment, and Content Programme integration (`:329-388`).

The submitted integrated plan's operating outcome names only fast/standard entry, a retrieval runtime, and false-scarcity resistance (`plans/canonical-research-workflow-near-term-strategic-improvements-implementation-plan.md:13-21`). It includes only the local trial and says canonical adoption remains deferred “regardless of trial outcome” (`:124-128,186`).

The Sector Intelligence evidence does not make canonical adoption safe without a trial, but it does show that the underlying mechanism is real: the local pilot passed at its 85–90% bar, the workflow integration is fail-closed, the four regression suites currently pass 82/82, and approved judgment demonstrably shaped three material prose passages. The same records explicitly limit that proof to a local, narrow micro-pilot and identify the missing canonical, expanded, and QC behavior (`projects/axcion-sector-intelligence/logs/work-loop/analyst-judgment-layer-local-pilot.md`; `.../judgment-layer-workflow-integration.md`; the four `check-judgment-*.test.sh` suites).

**Practical consequence if implementation begins unchanged.** Axcíon can spend the entire near-term programme improving transport while consequential writing still has no canonical approved analytical authority. Downstream agents may remain structurally free to invent or settle theses that the founder never approved. The hardest strategic improvement is omitted rather than sequenced behind its evidence gate.

**Required correction.** Keep the real local trial first, but make its pass/fail evidence a gate inside this plan. Add conditional canonical slices for: the generalized artifact and context contract; independent judgment QC plus founder approve/revise/reject; Stage 3 orchestration; downstream propagation and QC; deployment/synchronization; a real Sector Intelligence proof; and a current Editorial V2 Content Programme handoff before drafting. Add a specific operator gate for canonical judgment adoption. Define what trial evidence opens those slices and what failure stops them.

### P1 — The launch-period structured-statistics lane is dropped without a valid evidence trigger

**Factual finding.** The retrieval plan calls structured data the largest capability gap for macro/sector work, marks PxWeb/SDMX retrieval as “automate now,” ranks it P4 in launch-month priorities, and says it closes the biggest capability gap for macro/sector evidence (`plans/research-retrieval-layer-improvement-plan.md:32-34,52-71,101-105,121-149`). The submitted plan moves C3 outside the near-term boundary and supplies only “first follow-on after S4,” with no empirical trigger or decision that justifies dropping a launch-month requirement (`plans/canonical-research-workflow-near-term-strategic-improvements-implementation-plan.md:114,188`).

Current first-party documentation confirms the premise remains viable: [SCB operates PxWebApi v2](https://www.scb.se/en/services/open-data-api/pxwebapi/pxwebapi-2.0), while Eurostat exposes current [SDMX 3.0](https://ec.europa.eu/eurostat/web/user-guides/data-browser/api-data-access/api-getting-started/sdmx3.0) and [Statistics/JSON-stat](https://ec.europa.eu/eurostat/web/user-guides/data-browser/api-data-access/api-getting-started/api) APIs. A thin first lane does not require a general data platform.

**Practical consequence.** The new “retrieval runtime” would still route official macro and sector statistics through general web research, leaving the stated largest evidence capability gap intact and weakening the claimed macro/sector/trend outcome.

**Required correction.** Add a bounded post-S4 statistics slice: one PxWeb v2 provider and one Eurostat SDMX/JSON-stat path; request-file input; raw response plus normalized CSV/JSON; provider/table/series identity, query, retrieval time, checksum, and access-log entry; fixture tests plus one real pull from each grammar. Expand providers only on a second demonstrated need.

### P1 — The programme benchmark measures several outcomes but does not set delivery thresholds for throughput, turnaround, or total AI effort

**Factual finding.** The submitted benchmark records elapsed time, operator minutes, relay events, model/API cost or tokens, artifact count, and quality, but delivery thresholds cover relay events, operator minutes, main-session payload bytes, and quality only (`plans/canonical-research-workflow-near-term-strategic-improvements-implementation-plan.md:151`). There is no threshold for accepted outputs per operator hour, wall-clock turnaround, or total model/API effort. Therefore “substantially more research output” and “substantially less AI effort” remain untestable even after the previous review's correction.

**Practical consequence.** The programme could pass while moving the same work into more API/model calls, taking longer end to end, or producing no higher accepted throughput.

**Required correction.** Add numeric or explicit no-regression conditions for accepted-output throughput, R1/R2 wall-clock time, and total measured model/API tokens or cost. Keep operability separate from improvement and label a sample too small for stable conclusions provisional.

### P1 — S6 does not define a sufficient trigger for later adoption or cover all authority states

**Factual finding.** S6 requires a real proposal, founder revision/approval, propagation, and token burden, but its deterministic floor is only the existing local suites. Those suites prove the narrow local contract; they do not prove the expanded insight fields, insight ladder, independent judgment QC, current Content Programme handoff, or a durable rejected state. The local pilot's own record says its completed-report proof is a three-passage shadow and that canonical adoption remains a separate decision.

**Practical consequence.** “Re-plan on the trial's evidence” gives a fresh agent no pass threshold, no bounded successor route, and no way to distinguish evidence that supports generalization from evidence that requires redesign.

**Required correction.** Give S6 an evidence memo with explicit pass/fail criteria, burden measures, real revision/approval behavior, deterministic rejection coverage, a gap map against the expanded canonical contract, and a terminal rule: pass opens the named conditional adoption slices after operator authority; fail stops those slices and names the smallest contract to revise.

### P1 — The Perplexity slice still leaves a major runtime decision to the implementation agent

**Factual finding.** S4 says “selected Perplexity endpoint” and requires a maximum-spend preview, but does not bind endpoint class, model/preset, output/tool-call ceiling, or the response fields that make actual access and cost auditable. Current first-party documentation distinguishes the [Agent API](https://docs.perplexity.ai/docs/agent-api/quickstart), [Search API](https://docs.perplexity.ai/docs/search/quickstart), and [Sonar API](https://docs.perplexity.ai/docs/sonar/quickstart); the Agent API supports token/tool ceilings, structured response output, [web-search/fetch tools](https://docs.perplexity.ai/docs/agent-api/tools/web-search), and usage, while current [pricing](https://docs.perplexity.ai/docs/getting-started/pricing) gives the tools and Search API different cost models. This is an architecture and spend decision, not a minor coding detail.

**Practical consequence.** A fresh implementation agent must rediscover the core design, and a nominal “spend preview” can be fictional if request ceilings and tool-call limits are not fixed before dispatch.

**Required correction.** Bind S4 to the Agent API relay shape intended by the source proposal, with one bounded compatibility proof before build that fixes endpoint, model or preset, token/tool ceilings, structured report schema, usage/cost capture, and direct-fetch provenance. Stop if a defensible worst-case spend cannot be computed. Do not build a provider abstraction.

### P1 — S2 is coupled to propagation repair more tightly than its policy change requires

**Factual finding.** S2's canonical evidence rule and its propagation to existing projects are distinct claims. The submitted plan makes S0 a dependency of S2 and allows an S0 rejection to close or re-scope S2, even though the canonical `stage-instructions.md` can be corrected for future deployments without claiming existing-project propagation.

**Practical consequence.** An operator decision against expanding sync/deploy scope could block a critical canonical evidence safeguard for every future deployment.

**Required correction.** Let the authorized canonical S2 rule land independently. Make S0 a dependency only for existing-project propagation and for slices whose real proof requires deployment into an existing project.
