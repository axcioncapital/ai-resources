# Mission: Lead EmailOS from its current state to a testable MVP

## Why
Patrik needs to continue developing EmailOS inside the Systems Builder project without depending on memory or blindly following commands. He should understand what uncertainty each phase removes, know which tool owns each decision, and recognise when the work is genuinely ready to move into implementation and pilot testing.

## Success looks like
- Patrik can identify the next EmailOS phase from the state of the case files.
- Patrik can choose the correct Claude Code, Codex, terminal, Project Planning, or `/new-project` action.
- Patrik can explain why implementation must wait until needs, MVP scope, and technical approach have separate approvals.
- Patrik can recognise the evidence required before calling the result a testable MVP.

## Constraints
- The main SOP lesson must fit on one printable page.
- Use plain language suitable for a non-developer.
- Ground every process claim in the current repository rather than general software advice.
- Teach a reusable decision model instead of requiring memorisation of thirteen phase numbers.

## Out of scope
- Deciding A2 or A3 on Patrik's behalf.
- Selecting EmailOS's final CRM, architecture, or implementation technology before Phase 10.
- Implementing EmailOS in this teaching workspace.
- Designing the post-MVP product roadmap beyond what is needed to reach the first controlled pilot.
