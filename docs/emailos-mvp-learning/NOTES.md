# Teaching Notes

- Patrik wants a teaching guide, not a Codex-style compliance checklist.
- Always connect a command to the uncertainty it removes.
- Keep the main lesson to one printable page.
- Use EmailOS's real current state and exact repository commands.
- Prefer the reusable ownership model: route → define → create project → develop capability → release.
- Teach commands as lifecycle owners, not as a flat sequence:
  - `/leverage-idea` routes rough, owner-uncertain notes; EmailOS is already past it.
  - Systems Builder owns the approved system definition.
  - Project Planning + `/new-project` establish the project and initial technical implementation.
  - `/work-loop` owns the operating capability and consumes `capability-development`.
  - `/develop-ai-resource` owns only a skill, command, agent, prompt, or other AI artifact required by a slice.
- Be explicit that there is no live `/develop-capability` command; its responsibilities were consolidated into `/work-loop`.
- Surface the unresolved `/new-project` Stage 4–5 versus `/work-loop` Build–Prove overlap. Use the conservative no-duplication rule rather than hiding it.
- Do not create a learning record until Patrik demonstrates retrieval or application.
