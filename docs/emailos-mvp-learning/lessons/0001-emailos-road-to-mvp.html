Lesson 1 · EmailOS development

Learn the gates, not the phase numbers.

Your job is not to “move EmailOS forward.” Your job is to remove the next uncertainty without pretending a later decision has already been made. By the end, you should be able to name the next artifact, the tool that owns it, and the evidence required to move on.

Every gate answers a different question: What is true? What is the product? How should it work technically? Can the built loop survive a real test?

Product gate · V2 → MVP → Reviews 2–3

What must the system do—and what is the smallest complete loop?

First classify every V1 idea: Retain, Refine, Defer, Remove, Technical option, or Unresolved. Save the reconciliation and draft 03 without choosing technology. After Review 2, classify every V2 capability into MVP, Manual during MVP, Next, Later, Rejected, or Unresolved; draft 04 and run Review 3.

# Same packet commands; use phase 8 for V2 and phase 9 for MVP.

Why: V2 protects the approved need; Phase 9 protects you from building the full imagined future. Manual work is allowed when it still proves the core loop. Primary source

3

Solution gate · Approaches → V3 → Review 4

What is the simplest credible way to deliver that MVP safely?

Compare at least two approaches on effort, reliability, Gmail/CRM integration, human control, compliance, reversibility and failure recovery. Draft 05; state deliberately rejected complexity. Run QC, reconcile, and the Phase 12 Codex packet. Then translate approved V3 into 06-implementation-brief.md—adding no capability.

/session-start "EmailOS Phases 10–13 — select, red-team and brief the smallest credible solution"

Why: technology is now answering a bounded product question. Before this gate, it would quietly redefine the product. Operating source

4

Build gate · Plan → Spec → Implementation

Can a fresh implementation agent build and verify the approved loop without guessing?

In Project Planning, use 06 as the intake and point back to 01–05 as authorities. This is an adapter, not a second discovery cycle. Approve the context pack, then run the plan and spec cycles until both QC verdicts pass.

/context-builder <absolute-path-to-06> /plan-draft output/email-os/context-pack.md → /plan-refine email-os → /plan-evaluate email-os /spec-draft email-os → /spec-refine email-os → /spec-evaluate email-os # From the workspace root, after PASS: /new-project email-os

Why: the brief says what to build; the plan orders the work; the spec removes integration ambiguity; /new-project implements and verifies it. Planning source

MVP hypothesis—not yet a decision: select 10–15 qualified contacts in the CRM → assemble approved context → draft in the right language → founder approves → send via Gmail → return reply, permission and next action to the CRM.
Ready for pilot means: Stage 5 passes; a safe end-to-end dry run works; no message bypasses approval; CRM remains the buyer-state authority; suppression, reply and failure paths preserve state. Only then test a real controlled wave.

Retrieval practice · answer before revealing

A2/A3 are open, but a CRM tool looks promising. What next?

Close A2/A3 and Review 1. Tool selection belongs after the MVP boundary.

V2 is approved and contains twenty useful capabilities. What next?

Classify all twenty; keep only a complete, safe learning loop in the MVP.

When does “MVP defined” become “MVP ready to test”?

After planning, implementation and Stage 5 verification—not when document 04 is approved.
