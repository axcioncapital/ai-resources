Axcíon AI Resource Lifecycle Playbook — draft 1, 2026-07-30

Start here

I have a bunch of notes. What do I run?

Default for a messy idea dump: /leverage-idea path/to/notes.md It investigates and hands off. It does not implement.
Drafting rule: first draft the brief—outcome, evidence, examples, triggers, exclusions and proposed structure. Do not draft the final skill or command before the plan; the final resource file is implementation.
If the notes are really about… Owner Next command
A project outcome or repeatable operating ability Operating capability /work-loop
A new skill, command, agent, hook, prompt, script or persistent instruction AI artifact /develop-ai-resource
A skill gap you only want to record for later, without investigation now Intake /request-skill
A known, settled change to an existing skill Existing skill /improve-skill
A settled correction to another existing resource Existing object /work-loop
A symptom whose root cause is unknown Investigation $resolve-repository-problem in Codex
A one-line cosmetic edit Tiny fix /tweak

Lane A

Develop an operating capability.

Frame→ Shape→ Build slices→ Prove→ Land
  1. Frame: state the operating outcome, owner and evidence of the need.
  2. Shape: define the smallest intervention, slices and falsification criteria.
  3. Build: implement one complete slice at a time.
  4. Prove: test against Shape's criteria using observed evidence.
  5. Land: adopt, hold or reject. Record the lifecycle status.
/work-loop "<the project must be able to…>"
If the capability needs a new AI artifact, `/work-loop` hands that component to `/develop-ai-resource`. The capability stream keeps the operating outcome and adoption decision.

Lane B

Create or materially expand an AI artifact.

  1. Distil and route rough notes. /leverage-idea path/to/notes.md Expected output: evidence-backed options, recommendation, implementation plan and a raw Resource Brief in inbox/.
  2. Qualify the artifact. /develop-ai-resource inbox/<brief>.md It checks the need, existing coverage, smallest mechanism, placement and complexity budget. No build, reuse, a habit change or deferral can be the correct answer.
  3. Use the selected build engine.
    • New skill → /create-skill
    • Existing settled skill change → /improve-skill
    • Prompt, reference or instruction → bounded direct draft
    • Command, script or hook → smallest implementation plus executable checks
  4. Apply the proportional independent review at the correct boundary. A new command or skill is high-consequence: give the approved implementation plan to Codex once for a risk-aware review before implementation. A normal consequential artifact gets one Codex review of the result after deterministic evidence exists. The build engine's own skill evaluation remains part of the engine and is not an extra general review.
  5. Verify three separate claims.
    • Is it well made?
    • Does it belong in the system?
    • Does it do what it claims?
  6. Choose a disposition. Ship, revise, defer or delete candidate. Archive an inbox brief when its disposition closes the intake question.
Why qualification comes before implementation: a well-written skill can still be the wrong mechanism, duplicate an existing resource or cost more to maintain than the failure it prevents.

Lane C

Fix an existing AI resource.

Condition Command Exit condition
Cosmetic, one inline edit /tweak target "change" Read-back proves the exact edit.
Skill + change + mechanism are settled /improve-skill target Feedback resolved, skill evaluated, evidence reviewed, operator approves.
Existing command, agent, script, hook, doc or process; correction settled /work-loop "need" Premises verified, route completed, evidence returned, stream closed.
Need, scope or mechanism is uncertain—or change materially expands the resource /develop-ai-resource "need" Artifact re-qualified before build.
Only a symptom is known $resolve-repository-problem in Codex Executable reproduction, supported cause, bounded repair or capability handoff, and proof.
A mid-session fault must be diagnosed and fixed now $resolve-repository-problem in Codex The same end-to-end resolver owns diagnosis, bounded repair, and proof.

Operator checklist

Do not pass a gate unless you can answer its question.

  • Need: What happens today, and what evidence says it matters?
  • Ownership: Is this an operating outcome, an artifact, or a correction?
  • Mechanism: Why is this the smallest reliable rung?
  • Plan: What changes, what stays out, and what would falsify success?
  • Review: Is the independent review proportional and non-duplicative?
  • Evidence: What was run and what was observed?
  • Decision: Ship, revise, defer, delete, adopt, hold or reject?
  • Close: Commit locally; do not push; run /wrap-session +telemetry for a substantive session.

When to stop

Stop and re-route when a premise is false, ownership is unclear, a change crosses the approved scope, an unresolved material review finding remains, or the candidate cannot be tested. A visible stop is safer than a plausible completion.
